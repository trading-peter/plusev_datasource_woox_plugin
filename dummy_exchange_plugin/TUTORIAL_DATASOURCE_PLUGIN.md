# Plusev Data Source Plugin Tutorial (Dummy Exchange)

This is a slim, copy/paste-first guide to get a *data source* plugin bootstrapped and working. It uses a **pseudo exchange** that returns dummy data so you can focus on the **boilerplate + lifecycle methods**.

The goal: you create a WASM plugin that the terminal can load, ask for metadata/config/rate limits, and call commands like `getMarkets` and `getOHLCV`.

> This tutorial mirrors the patterns used in `plusev_datasource_binance_plugin` and `plusev_datasource_woox_plugin`.

---

## 1) Minimal mental model: what the terminal does

When the terminal loads your plugin, it effectively treats it as a small service with a few required entrypoints.

### Lifecycle / required methods

Your plugin type must implement the `DataSourcePlugin` interface from `github.com/plusev-terminal/go-plugin-common/v2/plugin`. In practice you’ll implement these methods:

- `GetMeta() meta.Meta`
- `GetRateLimits() []plugin.RateLimit`
- `GetConfigFields() []plugin.ConfigField`
- `OnInit(config *plugin.ConfigStore) error`
- `RegisterCommands(router *plugin.CommandRouter)`
- `OnShutdown() error`

Why these exist:

- **Meta**: lets the terminal display the plugin and enforce resource permissions.
- **Rate limits**: lets the terminal throttle calls *before* your code is overloaded or the exchange bans you.
- **Config fields**: lets the UI render a settings panel and store these values.
- **OnInit**: where you create your client, read config, set credentials.
- **RegisterCommands**: how the terminal learns which commands you support.
- **OnShutdown**: clean up (optional but required by the interface).

### How exports work (important)

You register the plugin in `init()` (not `main()`), because the WASM exports generated by `go-plugin-common/plugin` must be available immediately.

Pattern:

```go
func init() {
  p := &MyPlugin{}
  plugin.RegisterPlugin(p)
}

func main() {}
```

## 2) The boilerplate you always need (skeleton)

Create a `main.go` that follows this structure:

1. `init()` registers your plugin.
2. `main()` is empty (required for WASM).
3. A plugin struct holds config + your client.
4. Implement lifecycle methods.
5. Implement command handlers.

Use the dummy implementation below.

## 3) Dummy exchange: what it returns

This pseudo exchange supports:

- `getMarkets` → returns 2–3 fake markets
- `getTimeframes` → returns static list like `1m, 5m, 1h`
- `getOHLCV` → returns deterministic fake candles for requested timeframe

Nothing touches the network.

## 5) Method-by-method: what to return and why

### `GetMeta() meta.Meta`

Purpose: identify the plugin and declare permissions.

Minimum fields that matter in practice:

- `PluginID`: must be unique (example: `"dummy-datasource"`)
- `AppID`: must be `"datasrc"` for data source plugins
- `Resources.AllowedNetworkTargets`: whitelist domains this plugin may call

If you do **not** whitelist a host, requests will be blocked by the runtime.

### `GetRateLimits() []plugin.RateLimit`

Purpose: terminal-side policing by command.

You define entries like:

- command name (`ex.CMD_GET_MARKETS`, etc)
- scope (`IP`, `APIKey`, etc)
- RPS and burst

Even if your plugin is “fast”, rate limits protect you from:

- UI refresh storms
- multiple panels requesting the same data
- accidental hot loops

### `GetConfigFields() []plugin.ConfigField`

Purpose: drives the config UI.

Typical patterns:

- return static slice
- or create your client if nil and delegate to `client.GetConfigFields()`

Config keys you choose here must match what you read in `OnInit`.

In this codebase, `plugin.ConfigField` looks like:

- `Name`: the config key (what you pass to `config.GetString("...")`)
- `Label`: human name shown in UI
- `Type`: a string like `"text"`, `"password"`, `"number"`, `"select"`
- `Encrypt` / `Mask`: how secrets are stored and displayed
- `Options`: a free-form `map[string]any` for type-specific settings (e.g., select choices)

Common credential field names you’ll see in existing plugins:

- `"key"` / `"secret"` (e.g., WooX)
- `"apiKey"` / `"apiSecret"` (e.g., Binance/Orderly)
- Sometimes an extra `"applicationID"`

### `OnInit(config *plugin.ConfigStore) error`

Purpose: build runtime state.

Typical responsibilities:

- store config pointer (`p.config = config`)
- create requester / HTTP client / websockets client
- read config values (api key, secret, base URL, testnet flag)
- set credentials on your client

If you forget to instantiate your client here, your handlers will crash or return “client not initialized”.

### `RegisterCommands(router *plugin.CommandRouter)`

Purpose: declare your API surface.

You register commands by name:

```go
router.Register(ex.CMD_GET_MARKETS, p.handleGetMarkets)
```

The command names come from `datasrc/exchange` package for the standard datasource commands.

### `OnShutdown() error`

Often `return nil` is fine.

Use it if you need to:

- flush logs
- close websocket connections
- stop goroutines

---

## 6) Quick checklist

- [ ] `init()` calls `plugin.RegisterPlugin(p)`
- [ ] `GetMeta().AppID == "datasrc"`
- [ ] `GetConfigFields()` returns the keys you read in `OnInit`
- [ ] `RegisterCommands()` registers at least `getMarkets`, `getTimeframes`, `getOHLCV`
- [ ] Each handler returns `plugin.SuccessResponse(...)` or `plugin.ErrorResponse(...)`

## 7) Build notes

Each repo here uses a `build.sh`. For a new plugin directory you typically:

- create `go.mod`
- run `go mod tidy`
- build to WASM with TinyGo (common) or Go wasm (depending on your runtime)
